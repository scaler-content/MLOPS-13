Giving a model's memory a proper home

The returns model needs to know each customer's history. This read gives that history a home, a feature store, then builds training data from it in a way that does not cheat, and measures exactly how much cheating would have flattered the model.

12,000orders, Oct 2025 – Sep 2026
1,440customers
15,598customer feature rows
0.331share of orders returned

In the previous lesson, the returns model was trained with a SageMaker training job and served from an endpoint. To get a prediction, the caller had to send the customer's history along with the order: how many orders the customer had placed before, how many of them came back, and how long ago they signed up. That works in a demo. A real checkout page only knows which customer is logged in, so something has to look the history up.

That something is a feature store. Section 1 explains what it is, using the shop's own data. The rest of the read builds one with SageMaker Feature Store, trains the model from it, and measures a mistake that is very easy to make on the way.

  • Explain what a feature store is for, how offline and online stores differ, and what training and serving skew is.
  • Turn raw orders into customer feature rows, each with the time it became true.
  • Create an offline-only feature group from Python, and know the one bucket permission its role needs.
  • Measure how long written records take to show up, and query every stored version with Athena.
  • Build point-in-time and naive training sets, and quantify the gap with AUC.
  • Recognise quiet write failures, and clean up what deleting a feature group leaves behind.

01Why a feature store

Before building anything, it helps to see the problem clearly. It starts with three numbers the previous lesson's model used.

1.1Where the previous lesson left off

The model used three numbers about the customer: prior_orders, prior_returns and customer_tenure_days. A number a model takes as input is called a feature. These three describe the customer rather than the order, and they change over time. Every new order adds one to prior_orders. Every return adds one to prior_returns.

Two different parts of the system need these numbers, and they need different versions of them.

  • Training needs them for past orders. For an order placed last December, it needs the customer's history as it was last December.
  • The endpoint needs them for an order happening right now: the customer's history as it is today.

Previously, both got the numbers the simple way. The training file came with them already filled in, and the caller worked them out and sent them with every request. So two separate pieces of code computed the same thing. If they ever count even a little differently, say one includes today's order and the other does not, the model sees numbers at checkout that do not match what it learned from. This is training and serving skew. Nothing reports an error when it happens. The predictions just get worse.

1.2What a feature store is

A feature store is a database built for features. The features are worked out once, by one piece of code, and written to the store. Training and the endpoint then both read them from the store, so they always see the same numbers.

The two needs from 1.1 are different, so a feature store keeps the data in two forms. A bank account is a good picture of the difference. Your bank statement lists every transaction with its date, so you can work out what your balance was on any day in the past. The banking app's home screen shows only today's balance, but it shows it instantly.

  • The offline store is the statement. It keeps every value a feature has ever had, with the time it became true. Training reads it.
  • The online store is the home screen. It keeps only the latest value for each customer and answers a lookup in milliseconds. The endpoint reads it.

AWS's feature store is SageMaker Feature Store, and it has both halves. This read builds the offline store and trains the model from it. The next part adds the online store and connects it to an endpoint.

1.3The project, one step further

The shop still wants to know, at checkout, how likely an order is to come back. The label is still returned: 1 if the order was sent back, 0 if not. What changes is the data. The previous lesson had one row per order, with the customer's history already filled in as columns. This one starts a step earlier, from the raw orders, where each order only says which customer placed it.

The new file, returns_events.csv, holds 12,000 orders from 1,440 customers, placed between October 2025 and September 2026. About a third of them, 0.331, were returned. Most customers order many times over the year, so their history keeps changing.

1.4The question this read answers

Step 4 hides the most important decision. A customer has many rows in the offline store, one for each change. When you build the training row for one of their orders, which of those rows do you use?

The core question

The honest answer is the row that was true just before the order was placed. That is all the checkout page could have known at that moment. The easy answer is the customer's latest row, because it is the one an ordinary customer table would hold. But the latest row knows things that had not happened yet when the order was placed, such as whether that very order came back. Section 7 builds the training data both ways and measures how far apart they are. The gap is big enough to fool you.

To try any of this, the platform from the previous lesson has to come back first.

03Turning orders into customer features

The platform is back and the raw orders are in the bucket. The first step of the pipeline is features.py. It reads the orders and works out each customer's history: the same three numbers as before, plus a return rate.

A customer's history changes at two kinds of moment.

  • When they place an order. orders_so_far goes up by one.
  • When a return becomes known. The shop only learns that an order came back some time after it was placed. This file uses 14 days, set as RESOLVE_DAYS, so returns_so_far goes up 14 days after the order, never on the day itself.

features.py writes one row for every such moment. Each row has six columns.

ColumnMeaning
customer_idWhich customer the row is about.
event_timeWhen the row became true, as text such as 2025-10-13T00:00:00Z. The T and the Z matter, as section 9 shows.
orders_so_far, returns_so_farThe counts at that moment.
return_rate(returns_so_far + 1) / (orders_so_far + 5). The extra 1 and 5 pull a customer with few orders toward 20%, so one return out of one order does not read as a 100% returner. With no orders and no returns it gives exactly 0.2, a value section 7 reuses.
tenure_daysDays since the customer signed up, at that moment.

orders_so_far, returns_so_far and tenure_days are the previous lesson's prior_orders, prior_returns and customer_tenure_days with new names. The difference is that every row now also says when it became true. If two things happen to the same customer on the same day, they go into one row.

Keep this in mind until section 7

A row's counts include everything up to and including its own moment. The row stamped on the day of an order already counts that order.

3.1Where the 15,598 rows come from

Across all customers, 12,000 orders became 15,598 feature rows. Every order makes a row on the day it is placed, and every return makes a row 14 days later. When two of these fall on the same day for the same customer, they share one row. count_rows.py checks that sum by writing each order and each return as a (customer, day) pair and removing repeated pairs, the same merging features.py does.

count_rows.pyverifies the total
Output

These rows are ready for a feature store, and Feature Store has a name for each part of them. One row is a record. The column that says who a record is about, here customer_id, is the record identifier. The column that says when it became true, here event_time, is the event time. A customer can have many records, one for each change. When C-00001 placed their third order, a new record said orders_so_far was 3. The record before it, which said 2, is still true about the past. It is just no longer the latest. This is the bank statement from section 1.2: every version is kept, so you can ask what a customer looked like on any day.

04Creating a feature group from code

The rows from features.py exist only in memory so far. Before Feature Store can keep them, it needs to know what a row looks like. That description is the feature group. It says which column is the record identifier and which is the event time, lists every feature with its type, and says where the records are kept: the offline store, the online store or both. Think of it as the definition of a table, with the rows added later.

create_feature_group.py uses the sagemaker client in boto3, the AWS library for Python the previous lesson also used. It works in three steps.

  1. It asks whether a group called returns-customers already exists, with describe_feature_group. If it does, the file stops there.
  2. It creates the group with create_feature_group.
  3. Creating a group takes a little while, so it asks for the status every five seconds until it stops saying Creating, then prints what Feature Store set up.

The settings follow the anatomy above. customer_id is a String, though IDs often look like numbers, and section 9 shows what goes wrong otherwise. The URI of the offline store has no / at the end. There is no OnlineStoreConfig, so this group has no online store. The file passes the space's own role as RoleArn.

create_feature_group.pyoffline store only
Output
  • status says the group was ready after 27 seconds.
  • glue table is a table Feature Store made for you in AWS Glue, a list of tables kept by AWS. Each table says which columns some files in S3 have. Athena reads this table to know how to query the offline store's files with SQL. Feature Store put it in a database called sagemaker_featurestore and named it after the group, with a number on the end.
  • offline store is the S3 folder where the records will be kept. It starts with the feature-store prefix from the file, and Feature Store added the rest. The folder ends with the group's name and the same number, so every group gets a folder of its own.

Running the file again does nothing: it sees the group already exists.

One permission that is easy to miss

05Ingesting the features

The feature group is ready, but it is empty. ingest.py fills it in three steps.

  1. It reads the raw file from S3 and runs customer_features on it. That gives the 15,598 rows.
  2. It sends each row to Feature Store with put_record. One call writes one record.
  3. It keeps eight of those calls going at the same time.

put_record is not on the sagemaker client that created the group. Records are written and read through their own client, sagemaker-featurestore-runtime, just as the previous lesson called endpoints through sagemaker-runtime. Each call takes the group's name and one record as a list of feature names and values. Every value is sent as a string, even the numbers; the types in the feature group decide how each is stored.

Step 3 is about speed. A call spends almost all of its time waiting for an answer over the network, and there are 15,598 calls to make. Python's ThreadPoolExecutor keeps eight going at once, so while one waits, the others are already on their way.

ingest.py8 threads, one put_record per row
Run it once

A second run writes every record again, and the offline store keeps both copies, as section 9 shows.

5.1Did it arrive? Asking Athena

put_record returning without an error only means Feature Store accepted the record. It does not mean the record is in the offline store yet. To know that, you have to look in the offline store, and that is Athena's job. Athena runs SQL on the files in S3, and the Glue table from section 4 tells it what columns they have. There is no server to look after, and Athena bills by the data each query reads.

Several scripts from here on send queries to Athena, so query.py holds the shared part. Its function run(sql) starts a query with start_query_execution on boto3's athena client and checks every second until it has finished. Athena writes every result to S3 as a CSV file, here under athena/ in your bucket. run reads that file back and returns a pandas DataFrame. On import, the file also asks the feature group for its Glue database and table with describe_feature_group, so no table name is typed by hand.

query.pyshared Athena helper

wait_offline.py watches the offline store fill up. Every 30 seconds it counts the files in the group's S3 folder. Once there are some, it also counts the rows Athena can see. It stops when Athena sees all 15,598 rows, or after 25 minutes with a message saying how far it got. Both scripts print the clock time when they start and end, so their outputs can be lined up.

wait_offline.pypolls files in S3, then rows in Athena

ingest.py finished at 08:48:57. Yet for the first 301 seconds the offline store had no files at all. The next check, at 338 seconds, found 10,863 files and Athena saw all 15,598 rows at once, at 08:54:13, 5 minutes 16 seconds after the last record was written.

The quiet part of an offline store

For more than five minutes after every write had succeeded, a training set built from the store would have had no rows at all. Every query would have succeeded, and nothing would have said the data was missing. The safe habit: count the rows you wrote, count the rows the offline store has, and only build training data when they match.

5.2Small files, and where they live

15,598 rows arrived as 10,863 files, about 1.4 rows per file. Feature Store writes the offline store in small batches as records come in, and never merges them. For a few thousand customers that does not matter. For millions of records it makes every Athena query slower, because each query has to open every file. That is one reason AWS also offers the Apache Iceberg table format for the offline store, which can merge small files. This read keeps the default format, because its files are the easiest to look at.

07Point-in-time correctness

Section 1.4 asked the key question. A customer has many rows in the offline store, so which one goes with each order? The honest answer is the row that was true just before the order was placed. Joining each order to that row is called a point-in-time join. training_set.py builds the training data this way, and also the easy way, so the two can be compared. It does everything with SQL, sent through run from query.py, in four steps.

  1. It gives Athena a table for the raw orders. The orders are not in the feature store; they are a plain CSV under raw/events/, and CREATE EXTERNAL TABLE lets Athena read it.
  2. It joins each order to one customer row, once the easy way and once the honest way.
  3. It lays out each joined row the way the XGBoost container wants it with xgb_rows: label first, then the numbers, then one column per category and payment method, no header.
  4. It splits the rows by date. Orders before 1 July 2026 go to training and the rest to validation.

Step 2 is where the two sets differ. Both joins read from FEATURES, which keeps the newest copy of each customer row, because a retried write can leave two copies (section 9).

NAIVE

Gives every order the customer's latest row. This is what you get by joining orders to an ordinary customer table that holds today's values.

PIT

Gives every order the latest row from strictly before the order date. It turns both dates into timestamps, ranks matching rows newest first with row_number(), and keeps the top one.

In the honest join, an order with no row before it, such as a customer's first order, gets 0 orders, 0 returns and a return rate of 0.2 from FILL. Its tenure is still known from signup_date, so the SQL works it out with date_diff.

7.1Why strictly before

A row's counts include the order placed at its own moment. C-00001 placed an order on 22 December 2025, and the row stamped 22 December already counts it, with orders_so_far at 4. At checkout, that order has not been counted yet. The checkout would see the row before, from 21 December, with 3 orders and 2 returns. So the join must use <, not <=.

One character, every order

With <=, the mistake would not hit a few orders. It would hit all of them. features.py writes a row on the day of every order, so every one of the 12,000 orders would be joined to its own day's row, which already counts the order being predicted. No order would be left without a row either, so the result would look tidier, not worse.

Each job reports AUC on its own validation set. The naive model scored 0.832. The point-in-time model scored 0.721. If this were all you saw, you would ship the naive one. It looks about 0.11 better.

But the naive model was checked on naive rows. Its validation rows carry each customer's latest values too, so it was graded on the same leak it learned from. The question that matters is how it does on the rows it will really get in production, where the features come from before each order. The point-in-time validation rows are exactly that.

8.1Scoring both models on honest rows

score.py does this in three steps. The model runs on the space itself, so no endpoint is needed.

  1. It asks SageMaker for the newest finished training job with naive or pit in its name, with list_training_jobs, and finds where that job saved its model.
  2. It downloads the job's model.tar.gz from S3 and unpacks it. Inside is one file, xgboost-model, which the xgboost library loads with load_model.
  3. It scores the point-in-time validation rows, fs-validation/pit/validation.csv, and prints the AUC, worked out with scikit-learn's roc_auc_score.
score.pyscore a model on honest rows

The honest model scored 0.721, the same as its training job reported, because it is the same model on the same rows. That agreement is a useful check that score.py reads the files the way the container did. The naive model scored 0.714 on honest rows. Its offline score of 0.832 was off by 0.118, about 0.12. Served honestly, it is no better than the honest model, and here slightly worse.

The real damage

The model itself is not much worse. What goes wrong is every decision made from the 0.832. A team would expect a far better model than it got, and the drop would only show up after launch. Nothing in the training job reports a problem. Only a validation set built the honest way tells the truth.

8.2Why the latest row scores so well

Look at C-00001 again. Their latest row says 14 orders and 11 returns. The naive join gives that same row to every one of their orders, even the first one in October 2025. So every training row already knows how many of the customer's orders will come back, including the order being scored. The honest row for the 22 December order says 3 orders and 2 returns, which is all the shop knew that day. (Try it in the explorer above.)

A model trained on the latest rows learns to read those future returns. Its validation rows hold them too, so it scores well there. At checkout they are not there, and the score falls to what section 8.1 measured.

8.3When a feature store is more than you need

Look at what did the work here. The offline store kept every row, but it did not pick the right row for each order. The SQL in training_set.py did that. For one model trained and scored in batch, a table of dated customer rows in S3, joined with the same SQL, gives exactly the same correctness with no feature group at all.

09Failure modes

A wrong join is one way to spoil training data. Bad records are the other. Feature Store checks some things when you write, and lets others through without a word. failures.py writes deliberately bad records, so you can see each one before you meet it in real data. Its bad writes go to a separate, throwaway feature group, returns-failures, with the same features, created by the file itself the first time it is needed.

The file takes one word that picks the test: types writes bad values for number features; event_time writes event times in different formats; show reads back what the throwaway group kept; duplicate writes five rows to the real group a second time. For each record the first two print accepted, or REJECTED with the error Feature Store sent back.

failures.pypython failures.py types | event_time | show | duplicate

9.1Types

A tempting shortcut is to read the data with pandas and turn each column's dtype into a feature type. Tried on two lines of CSV, it goes wrong twice, and nothing complains.

ColumnWhat the CSV holdspandas reads it asGuessed typeRight answer
customer_id00123int64 → 123, leading zeros goneIntegralString
orders_so_far3, (missing)float64 → 3.0, NaNFractionalIntegral

That is why create_feature_group.py writes every type out by hand. Now, what the store itself does with bad values:

The first three bad values ("3.0", "abc", "nan") were rejected, with a message naming the feature and the type, and so was "nan" for return_rate, which is Fractional. These are the safe failures. A column that pandas quietly turned into decimals would hit the first one, because str(3.0) is "3.0", and put_record would refuse it loudly.

The one that gets through

"007" was accepted. The store read it as the number 7, and the offline store confirms it: C-TYPE-3 is stored with orders_so_far = 7. For a count that does not matter. For an ID declared Integral, it means 007 and 7 become the same customer, and no error ever says so. Keep IDs as String.

9.2Event time

Event time is checked strictly. A space instead of the T was rejected, and so were both kinds of epoch number, in milliseconds and in seconds. The space is the one to remember, because it is exactly what str() gives for a pandas timestamp. Had features.py not formatted event_time itself, every write in ingest.py would have failed this way.

The message lists two formats, with and without milliseconds, so .123Z was accepted as it says. A +05:30 offset is not in the list, and it was accepted anyway. Athena's from_iso8601_timestamp still reads such a time correctly, but as plain text, times with different offsets no longer sort in time order, so a text comparison would go wrong. Pick one format and write it everywhere.

Reading back what the throwaway group kept, only accepted calls left rows, and each accepted call adds one. The offset and milliseconds rows are stored exactly as sent, as text, because event_time is a String feature.

9.3Duplicates

A real ingestion job sometimes fails half way, and the usual fix is to run it again. failures.py duplicate does what that rerun does to the rows written the first time: it writes C-00001's first five rows to the real feature group again, with the same values and event times, then waits until the offline store shows them.

This is what the FEATURES step in training_set.py is for. It keeps only the newest copy of each customer row, so every order still matches one row. Without it, the result would depend on how the join is written. The row_number() join in PIT keeps only its top match, so it would still give one row per order. But another common way to write the join first finds each order's latest event time, then joins back to the table on that time. It would find both copies of a duplicated row, and every order matched to that row would appear twice in the training data, with no error.

Try it yourself · Checkpoint

Add a check to ingest.py, just before the thread pool starts, that stops the script if any row would fail or be quietly changed by the store. Check that orders_so_far, returns_so_far and tenure_days are whole numbers, that return_rate is a real number and not NaN, and that every event_time matches YYYY-MM-DDTHH:MM:SSZ. Then test it by changing one value in a copy of the rows.

The store caught only some of this section's mistakes, and it let "007" through without a word. A check in your own code is the only place all of them can be caught before anything is written.

10Tearing it down

That is the last of the feature store work, so everything it made can go. It made two feature groups, 10,874 files and three Glue tables: one for each group and one for orders. None of them bills by the hour. But deleting a feature group does less than its name suggests, so cleanup.py works in three steps.

  1. It deletes both groups with delete_feature_group and waits until each one is gone.
  2. It looks at what the deletes left behind: it counts the files still under feature-store/ and asks Glue whether each group's table still exists.
  3. It removes those leftovers: the files under feature-store/, athena/, fs-train/ and fs-validation/, then every Glue table in sagemaker_featurestore named after a group, plus orders.

The Glue deletes in step 3 are why the role has its own Glue policy. The role's AWS managed policies only let it delete tables whose names start with sagemaker_tmp_. The new policy allows glue:DeleteTable in the sagemaker_featurestore database and nothing else.

Each feature group was deleted in 5 seconds, yet both tables were still in Glue and all 10,874 files were still in S3. Deleting a feature group removes its definition and nothing it wrote. The offline store may be the only record of what a model was trained on, so keeping it is a fair default. But a team that creates and deletes groups for tests fills its bucket and its Glue catalogue with leftovers.

Step 3 finds the tables by listing them, not by asking each group, because of one more kind of leftover. If you delete a group and create it again, say to fix a mistake in its definition, the new group gets a table with a new number. The old table stays behind, and no group points at it any more.

11Summary

The previous lesson's model needed the caller to send the customer's history. This read gave that history a home. features.py turned 12,000 orders into 15,598 customer rows, one for every moment a customer's history changed, each stamped with its event time. A feature group with only an offline store took those rows and kept every one of them, as files in S3 with a table in Glue, so that Athena can read any customer as they were at any moment.

  1. Written is not visible. Every write succeeded within 22 seconds, yet the offline store showed nothing for more than five minutes. A training set built in that window would have been empty without a single error. Count what you wrote against what the store has before you build anything.
  2. Point-in-time correctness is the core. Joining each order to the customer's latest row gave a model that scored 0.832 offline. Joining to the row strictly before each order gave 0.721. Served honest rows, the naive model scored 0.714: the offline score had lied by about 0.12. And <= instead of < would have moved every one of the 12,000 orders onto the wrong row.
  3. Failures are quiet. A role without s3:GetBucketAcl gets an error that blames the S3 URI. "007" became 7 without a word. A +05:30 offset was let in though the message does not list it. Writing rows twice left two copies of each. Deleting a feature group left all its files and its Glue table behind. Each was caught by reading what the store actually held.
  4. The join is your SQL, not the store's. For one batch model, dated rows in S3 and the same SQL would do. The store earns its place once an endpoint needs the latest row fast, and once several models share the same features.

Where this goes

The feature group has only an offline store, which is right for training and useless at checkout. The next part adds the online store, so that the endpoint can look up a customer's latest features by customer_id at request time and the caller sends only who is buying.
